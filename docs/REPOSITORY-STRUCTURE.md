# 仓库结构规划

## 第一阶段：维护三个上游 fork

- `blbl`：以 `blbl-api19` 为 Android 4.4 适配基线，主分支跟踪上游最新代码。
- `HTV`：独立验证直播、EPG、自动换源和 `armeabi-v7a` 构建产物。
- `LauncherTV`：维护轻量桌面、遥控器焦点和老系统安装兼容性。

每个 fork 保留上游网络关系。需要改动时使用功能分支和 PR，不直接覆盖上游分支的历史。

## 第二阶段：公共维护资料

组织 `.github` 仓库提供跨仓库默认的贡献、支持、安全、Issue 和 PR 模板。项目仓库有自己的规则时，以项目规则为准。

## 后续再考虑的仓库

只有出现实际需求后再创建，避免提前拆分：

- `compatibility-lab`：保存只读的 APK 元数据、API/ABI 检查脚本和设备验收记录，不保存商业内容源。
- `legacytv-config`：仅在明确来源和授权后维护用户自己的直播/影视配置示例。
- `docs`：当跨项目文档明显超过 `.github` 仓库承载能力时再单独拆出。

## 分支和发布约定

- `main` 或上游默认分支：跟踪可复现的基线。
- `compat/api19`、`compat/arm32`：针对旧电视的适配工作分支。
- `fix/...`、`feat/...`、`docs/...`：短期变更分支。
- 发布 APK 必须关联源码提交、构建工作流和 SHA-256；没有固定签名时明确标注测试包。
